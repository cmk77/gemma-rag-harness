# ADR-0001: 하네스 오케스트레이션 — LangGraph vs plain LangChain Chain

- 상태: 채택(Accepted)
- 일자: 2026-06
- 맥락 태그: 아키텍처, 에이전트, 제어흐름

## 맥락

RAG 에이전트는 단순 "검색→생성"이 아니라 **조건 분기와 재진입**이 필요하다.
이 프로젝트의 요구 흐름은 다음과 같다.

- 질의 유형에 따라 경로가 갈린다(검색 필요 / 검색 불요 / 범위 밖 거절).
- 생성된 답변을 검증하고, 근거가 부족하면 **검색으로 되돌아가 재시도**한다.
- 재시도에는 상한과 루프 가드가 걸려야 한다(무한 루프 방지).

구현 수단으로 두 가지를 검토했다.

1. **plain LangChain**: `LCEL`(LangChain Expression Language)로 Runnable을 `|`로 연결.
2. **LangGraph**: 노드와 엣지로 상태 기계(StateGraph)를 구성.

## 검토한 대안

### 대안 A — plain LangChain (LCEL 파이프)

```python
chain = router | retrieve | generate | verify
```

- 장점: 선형 파이프라인에 간결. 의존성이 적고 학습 곡선이 낮다.
- 단점:
  - **순환을 1급으로 표현하지 못한다.** verify→retrieve 재진입을 LCEL로 만들면
    `RunnableLambda` 안에 while 루프와 상태 딕셔너리를 손으로 끼워 넣게 되는데,
    이는 제어 흐름이 코드에 흩어져 추적·테스트가 어렵다.
  - 조건 분기(`RunnableBranch`)는 되지만, 분기 + 순환 + 상한이 겹치면
    파이프 표현이 빠르게 복잡해진다.
  - 각 단계의 상태 전이가 명시적이지 않아, "어느 노드에서 왜 멈췄는가"를
    로깅하려면 별도 배선이 필요하다.

### 대안 B — LangGraph (채택)

```python
g.add_conditional_edges("verify", verify_decision, {"retry": "retrieve", "end": END})
```

- 장점:
  - **순환과 조건 분기가 그래프의 1급 개념.** 재진입 루프가 엣지 하나로 표현되고,
    제어 흐름이 그래프 정의 한곳에 모인다.
  - `AgentState`(TypedDict)로 노드 간 상태 전이가 명시적 → 진단(diagnosis),
    종료 사유(stop_reason), 문서 풀(_doc_pool) 같은 메타를 상태에 실어 추적 가능.
  - 노드가 순수 함수에 가까워 **단위 테스트가 쉽다**(실제로 스텁 LLM/ES로
    재검색 루프 전체를 모델 없이 검증함).
  - 체크포인터·스트리밍·휴먼인더루프 등 향후 확장이 프레임워크 차원에서 지원.
- 단점:
  - 의존성과 개념(노드/엣지/상태)이 추가된다.
  - 단순 선형 작업에는 과한 추상화다.

## 결정

**LangGraph를 채택한다.**

결정적 근거는 **재진입 루프**다. 이 프로젝트의 핵심 가치(검증 실패 시 진단 기반
재검색)는 본질적으로 순환이며, 순환을 1급으로 다루지 못하는 도구를 쓰면
제어 흐름이 코드 곳곳에 숨어 유지보수성이 무너진다. LangGraph는 이 순환을
선언적으로 표현하게 해주고, 상태 기반 설계 덕에 종료 사유·진단을 깔끔히 추적할 수 있다.

선형이었다면 LCEL로 충분했겠지만, 이 시스템은 선형이 아니다.

## 결과

- `harness/graph.py`가 6개 노드 + 2개 조건부 엣지로 구성된 StateGraph.
- 재검색 루프(verify→retrieve)와 루프 가드(no_new_docs)를 엣지/상태로 표현.
- 노드별 단위 테스트가 가능해졌고, 스텁만으로 루프 동작을 회귀 검증함.

## 비고

LangChain을 버린 게 아니다. LLM 클라이언트(`ChatOpenAI`)와 프롬프트 추상은
LangChain을 그대로 쓰고, **오케스트레이션 계층만** LangGraph로 올렸다.
두 도구는 경쟁 관계가 아니라 계층이 다르다.
