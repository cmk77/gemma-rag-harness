# ADR-0002: 하이브리드 검색 융합 — RRF vs 가중합(Weighted Score)

- 상태: 채택(Accepted)
- 일자: 2026-06
- 맥락 태그: 검색, 랭킹, RAG

## 맥락

하이브리드 검색은 BM25(키워드)와 dense kNN(의미) 두 결과를 합쳐야 한다.
문제는 두 점수의 **스케일과 분포가 전혀 다르다**는 점이다.

- BM25 점수: 0 ~ 수십, 쿼리·코퍼스마다 범위가 달라짐(상한 없음).
- cosine 유사도: -1 ~ 1 (정규화 임베딩이면 0 ~ 1).

이 둘을 어떻게 하나의 순위로 합칠 것인가.

## 검토한 대안

### 대안 A — 가중합 (Weighted Score Fusion)

```
final = α · normalize(bm25) + (1-α) · normalize(cosine)
```

- 장점: 직관적이고, α로 키워드/의미 비중을 튜닝 가능.
- 단점:
  - **정규화가 까다롭다.** min-max 정규화는 쿼리별 점수 범위에 의존해
    배치마다 기준이 흔들리고, z-score는 분포 가정이 필요하다.
  - **α가 코퍼스·쿼리 유형에 민감.** 고유명사 질의는 BM25 비중이,
    개념 질의는 의미 비중이 좋은데, 단일 α로는 둘 다 잡기 어렵다.
  - 점수 스케일이 다른 두 검색기를 더하는 순간, 한쪽 분포가 합산을 지배할 위험.

### 대안 B — RRF (Reciprocal Rank Fusion) (채택)

```
RRF_score(d) = Σ_검색기  1 / (rank_constant + rank_in_list(d))
```

- 장점:
  - **점수가 아니라 순위만 쓴다 → 스케일·분포 보정이 원천적으로 불필요.**
    BM25의 절댓값이 얼마든 "그 리스트에서 몇 위인가"만 본다.
  - 튜닝 파라미터가 `rank_constant`(통상 60) 하나뿐이고 이 값에 둔감하다.
  - 검색기를 N개로 늘려도 동일 공식이 그대로 적용(확장성).
  - ES 8.x가 네이티브 `rrf` 리트리버로 지원 → 프로덕션 이관 시 애플리케이션
    레벨 구현을 ES 내장으로 교체 가능.
- 단점:
  - 점수의 **크기 정보를 버린다.** "1위가 2위를 압도적으로 능가"하는 경우의
    강도가 순위로 뭉개진다.
  - 미세한 비중 조절(α 같은)이 어렵다 — 순위 기반이라 연속적 가중이 안 됨.

## 결정

**RRF를 채택한다.**

핵심 근거는 **스케일 불변성**이다. 가중합의 가장 큰 실무 비용은 "정규화를
어떻게 안정적으로 할 것인가"인데, RRF는 이 문제 자체를 제거한다. 점수 크기
정보를 잃는 손해가 있지만, 검색 융합에서는 "정답이 상위 k에 드는가"가
"정답 점수가 정확히 얼마인가"보다 중요하므로 순위 기반이 합리적이다.

또한 ES 네이티브 지원 덕에 PoC(애플리케이션 레벨 RRF)에서 프로덕션(ES 내장 RRF)
으로의 경로가 매끄럽다.

## 결과

- `retrieval/fusion.py`에 RRF 구현(`rank_constant=60` 기본).
- `es_store.py`의 `hybrid_search`가 BM25·kNN을 각각 k*2개 가져와 RRF로 융합.
- ES 네이티브 `rrf` 리트리버 사용법을 주석으로 병기(라이선스/버전에 따라 선택).
- 검증: 두 검색기 모두 상위인 문서가 1·2위, 한쪽만 등장한 문서는 하위로 융합됨을 단위 테스트로 확인.

## 비고

RRF의 점수 크기 손실이 문제가 되는 도메인(예: 점수 차가 의미를 갖는 추천)이라면
재고할 수 있다. 다만 본 RAG에서는 상위 k 회수가 목표이므로 해당되지 않는다.
향후 필요 시 **RRF로 1차 후보를 좁힌 뒤 cross-encoder 리랭커로 정밀 재정렬**하는
2단계 구성으로 확장하면, RRF의 약점(크기 정보 손실)을 리랭커가 보완한다.
