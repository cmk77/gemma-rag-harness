# 사이드 프로젝트 기획서: 자급식 RAG 에이전트 하네스
### (㈜인포유앤컴퍼니 AI 엔지니어 공고 대응용)

> **목표**: 단일 사이드 프로젝트로 공고의 8개 자격요건 전부를 "코드 + 커밋 이력"으로 증빙한다.
> **핵심 스택**: Gemma 4 27B (코어 오케스트레이터) · LangGraph/LangChain (하네스) · Elasticsearch (벡터 RAG) · vLLM (서빙)
> **개발 도구**: Claude Code (공고의 "AI Coding Assistant 실무 활용" 항목을 개발 과정 자체로 충족)

---

## 1. 공고 분석 — 요건 → 프로젝트 매핑

이 공고는 "LLM 애플리케이션 운영 엔지니어 + 품질 엔지니어"의 결합이다. 연구직이 아니라 **프로덕션에서 동작하는 RAG/에이전트를 만들고, 측정하고, 개선하는** 역할이다. 따라서 사이드 프로젝트도 "동작하는 데모"가 아니라 **계측·평가·회귀 테스트가 붙은 운영형 시스템**으로 만들어야 평가자에게 의미가 있다.

| # | 공고 자격요건 | 프로젝트 커버 요소 | 산출 증빙 |
|---|---|---|---|
| 1 | Elasticsearch/Cosmos 등 벡터 DB 기반 RAG 구현 | ES 하이브리드 검색 (BM25 + dense kNN), RRF 융합 | `retrieval/` 모듈 + 인덱스 매핑 |
| 2 | LLM API/프레임워크(LangChain/LlamaIndex) AI 에이전트 개발 | **LangGraph 상태머신 하네스** (라우팅/검색/생성/검증 노드) | `harness/graph.py` |
| 3 | LLM 성능 최적화 (토큰/속도/정확도) + 프로덕션 운영 | vLLM 서빙, 토큰 예산기, 프롬프트 캐싱, p50/p95 레이턴시 계측 | `serving/` + 벤치 리포트 |
| 4 | 프롬프트 개선 + 생성형 AI 품질 검증 | LLM-as-Judge 평가 하네스 + 프롬프트 버전 관리 + 회귀 스위트 | `eval/` + 평가 대시보드 |
| 5 | Hugging Face/Ollama 오픈소스 모델 + 최신 NLP 스택 | Gemma 4 27B (HF Transformers / Ollama 양쪽 백엔드 추상화) | `models/backends.py` |
| 6 | Git 기반 협업 + 코드 리뷰 | 모노레포 + Conventional Commits + PR 템플릿 + CI(lint/test) | GitHub Actions |
| 7 | AI Coding Assistant(Claude Code, Cursor) 실무 활용 | 전 과정을 Claude Code로 개발, `CLAUDE.md` 작업 규약 포함 | 커밋 메시지/PR 본문 |
| 8 | 요구사항을 기술 문서로 구체화 + 커뮤니케이션 | 본 기획서 + ADR(아키텍처 결정 기록) + README | `docs/` |

**우대사항**(최신 논문 빠른 이해·전파, 오픈소스 기여)은 4번 평가 하네스에 "신규 기법 1개를 논문 기반으로 추가하고 ADR로 근거 기록" 트랙을 넣어 자연스럽게 충족한다.

## 2. 프로젝트 정의

### 2.1 무엇을 만드는가
**도메인 한정 RAG 에이전트 하네스 `gemma-rag-harness`.**

특정 지식 코퍼스(예: 사내 기술문서/오픈소스 프로젝트 문서 — Mozi의 경우 `mask` 검색 플랫폼 문서나 Elasticsearch 공식 문서가 적합)에 대해 질의응답을 수행하되, 단순 RAG가 아니라 **에이전트가 스스로 검색 전략을 선택하고, 답변 품질을 self-check하고, 부족하면 재검색하는** 구조다.

### 2.2 왜 이 형태인가 (공고 적합성)
- 공고는 "AI 에이전트 **및** RAG 시스템"을 동시에 요구 → 둘을 하나의 하네스로 묶는 것이 가장 직접적인 답.
- 공고는 "품질 관리"를 업무로 명시 → 평가 하네스가 부록이 아니라 **1급 컴포넌트**여야 한다.
- Gemma 4 27B 로컬 서빙은 "오픈소스 모델 활용 + 토큰/속도 최적화" 두 항목을 한 번에 증빙.

## 3. 아키텍처

### 3.1 LangGraph 하네스 그래프 (핵심)

```
                    ┌─────────────┐
   user query ─────▶│   ROUTER    │  Gemma: 질의 유형 분류
                    └──────┬──────┘  (사실질의 / 비교 / 요약 / 범위밖)
                           │
              ┌────────────┼────────────┐
              ▼            ▼             ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ RETRIEVE │ │  DIRECT  │ │  REJECT  │
        │ (ES 하이브│ │ (검색불요)│ │ (범위밖   │
        │  리드검색)│ │          │ │  안내)    │
        └────┬─────┘ └────┬─────┘ └──────────┘
             ▼            │
        ┌──────────┐      │
        │ GENERATE │◀─────┘  Gemma: 근거 기반 답변 생성
        └────┬─────┘
             ▼
        ┌──────────┐
        │  VERIFY  │  Gemma(다른 프롬프트): 근거 충실성 self-check
        └────┬─────┘
             │ 불충분 → RETRIEVE로 재진입 (최대 N회)
             │ 충실   → END
             ▼
           답변 + 출처
```

LangGraph의 `StateGraph`로 구현하고, 상태(`AgentState`)에 `query / route / docs / draft / verdict / retry_count`를 담아 노드 간 전달한다. 조건부 엣지(`add_conditional_edges`)로 VERIFY → RETRIEVE 재진입 루프와 retry 상한을 건다.

### 3.2 검색 계층 (요건 1)
- **인덱싱**: 문서 청킹(토큰 단위, 오버랩) → 임베딩(`BAAI/bge-m3` 등 다국어 SOTA) → ES dense_vector 필드 + 원문 text 필드 동시 색인.
- **검색**: BM25(키워드) + kNN(dense) 두 결과를 **RRF(Reciprocal Rank Fusion)**로 융합. ES 8.x `rank: rrf` 또는 애플리케이션 레벨 융합.
- **Cosmos DB 대비**: 공고가 Cosmos(vCore)도 언급하므로, 검색 백엔드를 인터페이스(`VectorStore`)로 추상화해 "ES 구현 + Cosmos 구현 교체 가능" 설계임을 README에 명시 → 공고 두 DB 모두 커버한 것으로 어필.

### 3.3 모델/서빙 계층 (요건 3, 5)
- **모델**: Gemma 4 27B. 라우팅·생성·검증 모두 같은 모델을 **다른 시스템 프롬프트**로 호출(단일 모델 다역할 → VRAM 효율).
- **서빙**: vLLM (`--quantization` 옵션으로 27B를 단일/듀얼 GPU에 적재). OpenAI 호환 엔드포인트로 띄워 LangChain `ChatOpenAI(base_url=...)`로 연결.
- **백엔드 추상화**: `models/backends.py`에서 vLLM / Ollama / HF Transformers 세 백엔드를 동일 인터페이스로 → 로컬 개발은 Ollama, 벤치는 vLLM.
- **최적화 증빙**:
  - 토큰 예산기: 컨텍스트 길이 모니터링, 검색 문서 동적 trimming.
  - 프롬프트 캐싱: 시스템 프롬프트/공통 지시문 prefix 캐시.
  - 계측: 요청별 입력/출력 토큰, TTFT, p50/p95 레이턴시를 구조화 로깅 → 벤치 리포트 자동 생성.

### 3.4 평가·품질 계층 (요건 4 — 공고의 핵심 차별점)
- **골든셋**: 코퍼스 기반 Q&A 50~100쌍 직접 구축(질문 / 정답 / 근거 문서 ID).
- **LLM-as-Judge**: 답변을 (a) 정확성 (b) 근거충실성(faithfulness) (c) 관련성 3축으로 채점하는 별도 판정 프롬프트.
- **검색 평가**: Recall@k, MRR로 RETRIEVE 노드 단독 성능 측정.
- **회귀 스위트**: 프롬프트/그래프 변경 시 골든셋 전체 재실행 → 점수 변동을 PR에 자동 코멘트(CI 연동).
- **프롬프트 버전 관리**: 모든 시스템 프롬프트를 `prompts/*.md`로 분리, 버전 태깅. "프롬프트 개선"이 커밋 diff로 추적되게.

## 5. 마일스톤 (4스프린트 / 약 6주, 주말 사이드 기준)

| 스프린트 | 기간 | 산출물 | 충족 요건 |
|---|---|---|---|
| **S1: 골격** | 1주 | 모노레포 셋업, Gemma 4 27B vLLM 서빙 기동, "검색 없는" 단일 노드 LangGraph로 end-to-end 응답 | 5, 6, 7 |

| **S3: 에이전트화** | 1.5주 | ROUTER/VERIFY 노드 추가, 조건부 재검색 루프, retry 상한 | 2 |

## 6. 포트폴리오 어필 포인트 (지원 시)

- **README 상단에 요건 매핑 표**(본 문서 1장)를 그대로 넣어, 평가자가 "이 프로젝트가 공고를 어떻게 커버하는지" 한눈에 보게 한다.
- **벤치 리포트**(토큰/레이턴시/Judge 점수)를 스크린샷으로 첨부 → "측정하는 엔지니어"임을 증명. 공고가 "성능 최적화"와 "품질 검증"을 명시했으므로 숫자가 가장 강력한 어필.
- **ADR**로 "왜 plain chain이 아니라 LangGraph인가", "왜 단일 모델 다역할인가"를 설명 → "기술 동향 파악 및 도입 검토" 업무 적합성 증빙.
- Claude Code로 개발한 흔적(`CLAUDE.md`, 커밋 메시지 패턴)을 남겨 "AI Coding Assistant 실무 활용" 항목을 자연 증빙.

## 7. 즉시 착수 항목 (S1 첫 커밋)

1. `git init` + `pyproject.toml`(uv 또는 poetry) + `CLAUDE.md` 작성.
2. `serving/vllm_launch.sh`로 Gemma 4 27B 기동 확인 (OpenAI 호환 `/v1/chat/completions` 응답 확인).
3. `harness/graph.py`에 노드 1개(GENERATE)짜리 `StateGraph`를 만들어 "질의 → Gemma 응답" 최소 루프를 통과시킨다.
4. README에 요건 매핑 표 + 아키텍처 다이어그램 초안 커밋.

> S1의 목표는 기능 완성이 아니라 **"Gemma ↔ LangGraph 배선이 살아있다"**를 증명하는 walking skeleton이다. 여기까지 가면 이후 노드는 같은 패턴의 반복이다.
